**The sweep and its corrected rule:**
- **How it works:** `iam:SimulatePrincipalPolicy` for every principal, with `sts:AssumeRole` on the member's `OrganizationAccountAccessRole` and `sts:AssumeRoot` on the member's root.
- **Why it first stopped:** the script still expected the admin's role to be allowed both actions. Since phase 1c, the permission set allows `AssumeRoot` only with one of the five root task policies, and the sweep supplies none, so `explicitDeny` is the designed result.
- **A user-approved control of three simulations confirmed this:**
  - the allowed task, into `ecp-workloads`: allowed;
  - a task policy that isn't one of the five: explicitDeny;
  - the allowed task with the management account's root as the target: explicitDeny.
- **The corrected rule:** the admin's role is allowed `AssumeRole`, its `AssumeRoot` without a task is `explicitDeny`, and every other principal is denied both.

| Principal | AssumeRole | AssumeRoot (no task) |
|---|---|---|
| the admin's Identity Center role | allowed | explicitDeny |
| `ecp-gha-deploy` | explicitDeny | explicitDeny |
| the other project's IAM user | explicitDeny | explicitDeny |
| `ecp-gha-plan` and the other project's six roles | implicitDeny | implicitDeny |

## Step 5: the state migration
**A check was replaced before the migration.** An offline test with a synthetic resource found that migrating from a *configured* local backend copies the state but leaves the local `terraform.tfstate` untouched. Terraform empties the local file only when no backend was configured before. So the planned check "the local state has no managed resources afterwards" could not pass. The user reproduced this and replaced the check.
