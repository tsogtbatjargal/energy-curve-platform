## The sweep, and an out-of-band IAM change
The bootstrap-window sweep ([ADR-0021](../adr/0021-dedicated-workload-account.md#the-bootstrap-window-phase-1b)) simulates `sts:AssumeRole` on another account's `OrganizationAccountAccessRole` and `sts:AssumeRoot` on another account's root, for each management-account principal.

- **Correction.** The sweeps before apply 3, including those recorded for applies 1 and 2, covered **roles only**. Their "only the admin role is allowed" result did not cover IAM users.
- **Before apply 3**, the sweep was widened to every non-service role **and IAM user**. It found **the other project's admin IAM user** **allowed both** actions, through its group `bedoux-admins` (`PowerUserAccess`, which allows `sts:*`, plus the managed `bedoux-iam-scoped`). That user has long-term access keys. Applies 1 and 2 had run with this path open; neither created an account, so nothing was exposed. The apply was stopped before any change.
- **The fix, approved by the user and applied by the user:** a new inline policy on the group.

| | |
|---|---|
| Target | group `bedoux-admins` (inline policy; the group and the user had none before) |
| Name | `ecp-no-cross-account-sts` |
| Document | exactly the deploy role's `NoCrossAccountRoles` and `NoRootSessions` statements ([ADR-0018](../adr/0018-workload-permissions-boundary.md), PR #25), for this account |
| SHA-256 of the approved file | `0e15d4b0ff97dcf772077b933518f3acd50e02eaa98a4d5716e44125861a655b` (415 bytes; `get-group-policy` read back equal) |
| CloudTrail | `PutGroupPolicy`, 2026-10-06 15:51:00 UTC, the admin's Identity Center session |

**Simulation of the other project's admin IAM user** (`iam:SimulatePrincipalPolicy`; "other account" is a placeholder account ID):

| Action | Resource | Before | After |
|---|---|---|---|
| `sts:AssumeRole`, `sts:TagSession`, `sts:SetSourceIdentity` | a role in its own account | allowed | allowed |
| `sts:AssumeRole`, `sts:TagSession`, `sts:SetSourceIdentity` | `OrganizationAccountAccessRole` in another account | allowed | explicitDeny |
| `sts:AssumeRoot` | another account's root | allowed | explicitDeny |
| `sts:AssumeRoot` | its own account's root | allowed | explicitDeny |

**Full sweep after the change, and again immediately before apply 3** (9 non-service roles, 1 IAM user):

| Principal | `AssumeRole` | `AssumeRoot` |
|---|---|---|
| the admin's `AWSReservedSSO_AdministratorAccess_*` role | allowed | allowed |
| the other project's admin IAM user | explicitDeny | explicitDeny |
| `ecp-gha-deploy` | explicitDeny | explicitDeny |
| `ecp-gha-plan` and the other project's six roles | implicitDeny | implicitDeny |

**This change is out-of-band.** It is not in any Terraform state, in this repository or in the other project's.
- **Who owns it:** this project, as a guard for ADR-0021's bootstrap window (W2) and, from phase 1c, for `AssumeRoot`. Keep it until the other project's user no longer has `sts:*`, or no longer exists.
- **Reversal** (needs the user's approval): `aws iam delete-group-policy --group-name bedoux-admins --policy-name ecp-no-cross-account-sts`. This reopens the path, so before phase 3 restricts the break-glass role's trust it would let that user's keys become administrator in `ecp-workloads`. Reverse it only together with another control, and re-run the sweep afterwards.
- **Risk that the other project's IaC removes it.** Today nothing would: a search of the other project's local repositories found no Terraform or CloudFormation for the group, its policies or any `*_exclusive` resource. Its `bedoux-iam-scoped` policy is versioned by hand (its ADR-0016), and its `verify-iam-boundary.sh` does not check the group's policy list. The deny would be lost if:
  - that project adopts IaC for the group with exclusive inline-policy management (for example `aws_iam_group_policies_exclusive`), or someone deletes inline policies there as cleanup;
  - the group is deleted and re-created, or the user is removed from the group;
  - a new management-account user or role gets `sts:*` some other way.
- **Detection:** re-run the full role-and-user sweep before every later ADR-0021 phase (1c, 2, 3, 5). Any principal other than the admin role that is allowed either action stops the phase.
