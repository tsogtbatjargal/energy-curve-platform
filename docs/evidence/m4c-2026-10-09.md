## R2 in AWS: the simulation, and a limit of the simulator
Each of the 30 scenarios in `tests/test_batch_iam.py` was run through `iam simulate-custom-policy` against the role's policy template with the workload boundary, and later through `simulate-principal-policy` on the 5 real roles.
- **28 scenarios agreed** between AWS, the local evaluator and the expectation. All 14 "must not be allowed" scenarios were denied.
- **2 could not be evaluated:** `logs:PutLogEvents` for the stage role and `logs:CreateLogStream` for the exec role. AWS's simulator returns `implicitDeny` for any request ARN of the form `…:log-group:/<name>:log-stream:<s>`, even under an Allow on `Resource: "*"`. The private script ran that control on every run and reported the two as "simulator cannot evaluate: slash-prefixed log group" only when the control was also `implicitDeny` and the local evaluator said allowed. An independent reviewer found the cause. The policies are not at fault, so no template or test changed.
- **The real proof** is in the first run below: both log groups received streams with events.

## The profile trap
`mise.toml` loads `.env`, which sets `AWS_PROFILE` to the management admin. An `AWS_PROFILE=… mise exec -- …` prefix is therefore overridden, and so is a profile set before `uv run` or any other mise shim.
- **How it showed:** the first `terraform init` against the real backend, meant to run as the member read-only role, failed with a 403 on a state key that does not exist. It had run as the management admin. An independent reviewer found this: as the member read-only role, the same read returns 404, as it should.
- **No write happened.** The failed call was a read.
- **The same trap hit the trust-review precheck** later: it ran against the management account and reported 18 roles instead of 9, which stopped the apply until it was understood.
- **The rule since:** set the profile inside the command (`mise exec -- env AWS_PROFILE=… terraform …`), run Python scripts with the virtual environment's interpreter, and print the caller's role and account from that same process before every AWS step. Now in the private gotchas notes.

## Two refresh-only applies
Both were needed because the provider reads some attributes back differently after a create (null instead of an empty value). A plan that refreshes these is not "No changes" until the state records them, and the stage-2 gate refuses drift.
- **Before stage 2:** 18 entries. The earlier text output showed only 1 of them, so drift is now judged from the plan JSON.

  | Kind | Entries |
  |---|---|
  | `tags` null → `{}` only | 9 |
  | `inline_policy` and `tags` (the 5 roles) | 5 |
  | `route` and `tags` (the route table) | 1 |
  | `egress` and `tags` (the task security group) | 1 |
  | `pending_confirmation` only (the subscription) | 1 |
  | `lifecycle_rule`, `policy`, `tags`, `versioning` (the data bucket) | 1 |

  Each inline policy equals that role's template, and the route, egress and bucket values equal their companion resources' values. An earlier re-plan had run seconds after the apply and reported the bucket's lifecycle configuration as missing; S3 had not yet propagated it. An independent reviewer confirmed that and the clean re-plan.
- **After stage 2:** 4 entries, all on resources planned no-op: the alarm (`dimensions`, `ok_actions`, `insufficient_data_actions` null → empty; `period` null → 0 on each of its four queries), the task definition and the state machine (`tags`), and the Lambda function (`tags`, `layers` null → `[]`).

## Step 7: one run and its replay
Run id `m4c-first-20261009`. The store was empty beforehand (0 objects under `store/`).
- **The execution** started once, through Step Functions, and finished `SUCCEEDED` in about a minute. The task logged `status=published`.
- **The replay** was one direct `ecs run-task` with the same run id, which reads the same staged pages. It stopped with exit code 0 and logged `status=already_published`. The pointer's version count, version ID and ETag were identical before and after.
- **Objects:** after the first run the store held 14 objects; after the replay, 15.
  - `staging/<run_id>/` has 2 (`page-0001.json` and `requests.json`);
  - the published version sits under `runs/` (9 objects);
  - `published/` holds 2 (the pointer `current.json` and `versions/00000001.json`);
  - `attempts/` held 1 record after the first run;
  - the replay added the second `attempts/` record. The 15 are therefore staging 2, published 2, runs 9 and attempts 2. The extra record is expected: every run records its attempt, and the replay changed nothing else.
- **The log-stream proof:**
  - `/aws/lambda/ecp-batch-stage` has 1 stream with 3 events, the first a Lambda `START` line;
  - `/ecs/ecp-batch-pipeline` has 2 streams (the run and the replay), each with 2 events.

  These are the real proof for the two scenarios the simulator could not evaluate: the stage role's `logs:PutLogEvents` and the exec role's `logs:CreateLogStream` both worked.
- **After the runs:** the alarm stayed `OK`; the sweep was unchanged; the trust review still shows 15 roles and the one accepted line; a re-plan with the digest shows 0 changes and 0 drift.

## A scan exception that appeared on the way
The day after the image was pushed clean, the `image` check began failing on every PR: the vulnerability database now lists `CVE-2026-78667` and `CVE-2026-97031` (Go standard library v1.26.7, fixed in 1.26.9) in `usr/local/bin/aws-lambda-rie`, the local-test emulator in the Lambda base image. The base image's own entry point script starts that emulator only when `AWS_LAMBDA_RUNTIME_API` is unset, which Lambda sets, and the Fargate task overrides the entry point.
- **The exception** (PR #49, [ADR-0020](../adr/0020-cloud-entry-points-and-batch-image.md) addendum): `.trivyignore.yaml` ignores exactly those two IDs on exactly that path and expires on **2026-11-08**. The CI log prints the suppressed findings, and an independent reviewer confirmed it lists exactly those two.
- **The pushed image** in ECR contains the same binary. It is rebuilt and pushed once AWS ships a fixed base, with a new digest and a new plan.
