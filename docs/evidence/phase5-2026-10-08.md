## The code change (PR #37)
- **What it adds:** `scripts/bootstrap_plan_check.py --change decommission`, the gate for a destroy-only plan. It accepts exactly the 8 deletes, with each object's name, and the 4 output deletes, and nothing else. It also checks the state, the instance variable, the caller and the source (no override, no JSON configuration, no module call).
- **Why a dedicated gate:** `scripts/policy_gate.py` counts only resources that remain. A plan that only deletes is therefore `VACUOUS` (exit 2) by design. A test pins both sides: the policy gate refuses the plan and the check accepts it.
- **Merged** at the approved head, giving `main` `f708d24`. One CI job on `main` hung while installing a browser. It was cancelled and its failed jobs were re-run, after which all seven checks passed.

## The account email (prerequisite, user-run)
**Why AWS had to change first.** The user set a new, readable `workload_account_email` in the git-ignored `infra/org/terraform.tfvars`. In AWS provider 6.67.0, `email` on `aws_organizations_account` forces a new resource, the update path handles only `name` and `parent_id`, and each refresh reads the address from Organizations. So the file alone would plan a replacement, which `prevent_destroy` refuses. The address therefore had to change in AWS through Account Management.

**Who can do it (read-only simulation, 9 roles and 1 IAM user):**

| Principal | `GetPrimaryEmail` | `StartPrimaryEmailUpdate` | `AcceptPrimaryEmailUpdate` |
|---|---|---|---|
| The AdministratorAccess Identity Center role | allowed | allowed | allowed |
| `ecp-gha-plan`, `ecp-gha-deploy`, and the other project's IAM user | allowed | denied | denied |
| The other project's 6 roles | denied | denied | denied |

The resource is the member account in the organization (resource type `accountInOrganization`). Control: `ecp-gha-plan` is denied both writes.

**The run.** The user enabled trusted access for Account Management, ran a reviewed script, and disabled trusted access again. The script reads the address from the file, prints neither the address nor the account ID, takes the one-time code at a hidden prompt, and checks the identity before every call.
- **First attempt:** `ValidationException`. The script's HCL parser returned the value with its quotes, so the address was sent quoted. The fix strips one matching pair of quotes and rejects any quote or whitespace. It was tested offline on synthetic files.
- **Third attempt:** `ConflictException`, which AWS's API reference gives for an address already in use. The user chose another address.
- **The final run:**

| Line | Result |
|---|---|
| Identity, target account, trusted access | PASS |
| `start-primary-email-update` | `PENDING` |
| `accept-primary-email-update` | `ACCEPTED` (the code arrived at the new address, so the user controls its inbox) |
| `get-primary-email` matches the file | **FAIL, unexplained** |
| Organizations `describe-account` matches the file | yes |

**The FAIL line is unexplained.** It is not counted as a pass.
- Organizations matched in the same run, and a later recheck also showed a match. So did the `infra/org` plans (precheck 8 below).
- `get-primary-email` was not called again, because that needs trusted access, which the user chose not to re-enable.
- Possible causes include propagation lag and an exact-match comparison that a case difference would fail. Neither was confirmed.

**Trusted access afterwards:** exactly 2 services, IAM and Identity Center. Account Management is not among them. This was checked read-only after the user disabled it.
