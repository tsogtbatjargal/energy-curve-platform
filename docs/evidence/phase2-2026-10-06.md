- **Access:** CLI access to `ecp-workloads` works.
- **Inventory:** the account holds only what AWS and this project created.
- **Break-glass role:** never used.
- **SCPs:** they behave as reviewed.
- **Root user:** it has no credentials.
- **Skipped steps:** 7 (delete) and 8 (re-audit), recorded below as deviations.

**Sanitized:** no account IDs, email addresses, plan files or plan JSON, and no names from the other project.

## Step 5: SCP checks, simulator only
**Method:** `simulate-principal-policy` in the member account, with the `ecp-readonly` role as the source.
- **Pass criterion:** `OrganizationsDecisionDetail.AllowedByOrganizations`. The overall decision isn't used, because `ReadOnlyAccess` denies some of these actions regardless of the SCPs.
- **Context:** every case supplies `aws:RequestedRegion` and `aws:PrincipalArn`. The simulator doesn't report missing context for SCPs, so a missing key could silently flip a result.
- **Controls:** each denial has a control that changes one thing.
- **`organizations:LeaveOrganization`** was never called for real.

| Case | Expected | Result |
|---|---|---|
| `ec2:DescribeInstances` in eu-west-1 | false | false |
| control: same in ca-central-1 | true | true |
| `organizations:LeaveOrganization` | false | false |
| control: `organizations:DescribeOrganization` | true | true |
| long-term root user (root ARN, no `aws:AssumedRoot`), `s3:ListAllMyBuckets` | false | false |
| control: same with `aws:AssumedRoot` = `true` | true | true |
| `AssumeRoot` session (root ARN, `aws:AssumedRoot` = `true`), `s3:DeleteBucketPolicy` | true | true |
| control: same, only `aws:AssumedRoot` dropped | false | false |

**Limits:** the root cases can only be expressed as context. A root principal can't be the simulated source or caller, so they test the SCP's conditions, not a real root request. Resource control policies aren't evaluated (none are in use). The eu-west-1 read in step 3 is the only live check of an SCP.

## Steps 7 and 8: skipped, as deviations from ADR-0021
- **What the ADR expected:** an `IAMDeleteRootUserCredentials` session (step 7), then a fresh audit session (step 8). Its acceptance said the root user shows no credentials "after `IAMDeleteRootUserCredentials`".
- **The decision (user, 2026-10-06):** skip both. Neither a delete session nor a re-audit session was opened.
- **Why:** step 6 found no root credentials to delete. AWS documents that "New accounts you create in AWS Organizations have no root user credentials by default", and that once centralized root access is on, "Member accounts can't sign in to their root user or perform password recovery for their root user" (IAM User Guide, *Centralize root access for member accounts*). Root-credential management has been on since phase 1c.
- **What changed in the ADR:** its phase 2 acceptance now reads: the audit shows no root credentials, and any that exist are deleted (then audited again), each session with its own approval.
