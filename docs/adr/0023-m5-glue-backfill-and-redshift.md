## Context
PLAN.md M5: a PySpark job on Glue reproduces the seasonal-shape parameters the Polars reference produces, and a Redshift Serverless workgroup loads and queries the curve and price history. The draft is done when the Glue backfill and a Redshift query have each run once. Only synthetic data reaches AWS (ADR-0011).

## Decision
### Data and code (M5a, this PR)
- **The history is generated, not uploaded.** `energy_curves.synthetic_prices` is the deterministic, seeded price function (moved out of `ingestion/synthetic.py`, which imports it back; a digest test pinned its output before the move). The Glue job calls it inside Spark, one task per slice of days, so no object is uploaded and nothing real can reach the job. The catalog has 6 series; 1983-01-03 to 2024-04-05 is 10,765 business days, about 64,600 rows. The shape estimate reads 5 series in the 2014 to 2024-04-05 window, about 13,000 rows. Spark is far more than the volume needs (ADR-0007 already says so).
- **One contract, two engines.** `energy_curves.curves.shape_core` holds the constants, `quantize_s`, `ShapeEstimationError` and the canonical parameter text; both `curves/shape.py` (Polars) and `jobs/glue/shape_job.py` (PySpark) use it. The job imports only PySpark, the standard library, `catalog`, `synthetic_prices` and `shape_core`; an AST test enforces this (no Polars, no HTTP client).
- **The parity test** runs in the existing `glue-compat` job (Python 3.11, Java 17, PySpark 3.5.6) on a one-year slice and on the full history, on a history generated in Spark and one generated in Python. It requires identical keys and `n_obs`, `s` within 1e-9, and, as the stronger check, identical canonical text and SHA-256 (a rounding-boundary flip is reported, not hidden). It also checks the exclusions (the negative-price day, a non-positive future), the error messages for a thin or missing group, a window that cuts a month, and byte-identical output across runs and partition counts. The 13 Spark cases take about 25 seconds, so CI runs the full history; no slice is needed.
- **Entry point:** `shape_job.main` writes `shape_params.csv` and `shape_params.sha256` under `--output`. Remote (S3) paths are exercised in M5b. *(Updated in M5c-0: the files are written under `--output/<JOB_RUN_ID>/`, followed by a completion record; see "Each run writes its own prefix" below.)*

### Stacks (M5b and M5c)
- **Two stacks** (ADR-0003, one job per AWS service): `infra/glue` and `infra/redshift`.
- **Glue (built in M5b, below):** `glue_version = "5.1"`, G.1X, 2 workers, no VPC, no crawler, no Data Catalog; the script and a bundle of the package modules in the stack's own bucket (`--extra-py-files`); a role with the workload boundary that writes only an `m5/` prefix; a log group. Run on demand. **No failure alarm** (decided 2026-10-10): the job runs on demand while its operator watches it, the batch stack's SNS topic lives in another state, and Glue reports run state through EventBridge rather than a CloudWatch metric an alarm could use without extra setup. *(Superseded by M5b: two log groups under `/aws-glue/ecp-shape`, below; the job writes one run prefix per run.)*
- **Redshift Serverless is permanent**, on demand to use: idle compute costs nothing, storage is under 1 GB. It is not part of the daily state machine.
  - `base_capacity = 4` (the documented minimum; the default is 128 RPU, $52.80 an hour), `max_capacity = 8`, and a daily usage limit of 3 RPU-hours with breach action `deactivate`. A plan check pins all three. *(Amended in M5c-1: 8 and 8, and a 4 RPU-hour limit, because ca-central-1 has no 4 RPU option; see below.)*
  - **AWS's default admin name, no password set, no network path.** The namespace sets none of `admin_username`, `admin_user_password`, `admin_user_password_wo` or `manage_admin_password`, so there is no password in state and no Secrets Manager secret. *(Exception, recorded below: the service reports its default admin name `admin` on the namespace.)* Access is IAM only, through the Data API, which maps the caller's IAM identity to a database user and needs `redshift-serverless:GetCredentials`. A new schema needs superuser or a granted privilege, but every user may create tables in `public`, so all tables live there with an `ecp_` prefix, created by the role that loads them. Whether the namespace creator is a superuser is not documented for the API path; the first session checks it with one statement, and the design works either way.
  - **Its own network:** a small VPC with 3 private subnets in 3 Availability Zones chosen from what the account reports, a security group with no ingress, no internet gateway, no NAT and no route to the internet, no enhanced VPC routing and not publicly accessible. AWS requires two AZs without enhanced VPC routing and the Terraform provider documents three subnets in three AZs; three satisfies both. These resources are free. The Data API is called by the caller, not from this VPC, so it needs no endpoint. Redshift's documentation says that with enhanced VPC routing off "Amazon Redshift routes traffic through the internet, including traffic to other services within the AWS network", and requires a VPC path only when it is on. That `COPY` from S3 works in a VPC with no internet path is therefore an inference, proven by the first session's first statement. **Fallback, a plan change:** enhanced VPC routing on plus one free S3 gateway endpoint (ADR-0004 allows gateway endpoints). *(M5c-1 note: with enhanced VPC routing on, traffic to S3 also needs an outbound rule on the workgroup's security group to the S3 prefix list, which the no-rule group of M5c-1 does not have; the fallback plan must add that rule, and the plan check, which allows none, changes with it.)*
  - **Roles** (all with the workload boundary, constants only, no wildcard with a write): one for Glue, one that Redshift uses for `COPY` from the `m5/` prefix, one for the caller of the Data API.
- **Queries (about five):** the latest curve per series, the WTI to Brent spread by tenor, contango and backwardation days, revisions per month, and one window function (a rolling percentile). The shared queries run against the local Postgres in CI where the dialects overlap; `COPY` and anything Redshift-only stay in a separate file that `sqlglot` parses, and one Redshift session confirms the results.
- **Applies** keep the M4c pattern: a stack-specific plan check, the policy gate, a saved plan, a hash approval, identity printed first, no apply from 11:45 to 12:15 Toronto, post-apply read-only checks, the plan file deleted afterwards.

### The first cloud run failed on its arguments (2026-10-10), and the fix
The first run (`jr_fcb3e5d62…`) failed in 29 seconds with `SystemExit: 2`: the script called `argparse.parse_args()`, and Glue appends its own arguments to the script's command line (`--JOB_NAME`, `--JOB_ID`, `--JOB_RUN_ID`, `--continuous-log-logGroup`, `--enable-continuous-cloudwatch-log`, `--enable-continuous-log-filter`, `--glue-di-packages-correlation-ids`, `--internal-lib-urls`, `--tenant-internal`; `--extra-py-files`, `--enable-metrics` and `--job-language` were consumed by Glue). Nothing was written, no `AccessDenied` occurred, and the script did import its modules from the bundle on the driver. The local tests had never passed Glue's extra arguments.
- **The fix:** `parse_known_args`, with `allow_abbrev=False`; every argument the job uses is `required=True` with no default (so a missing or misspelled argument fails loudly, and `--out` does not stand in for `--output`); dates are strict `YYYY-MM-DD`; the ignored arguments are logged **by name only**, because their values can be URLs and ids. The stack now passes all six of the script's own arguments, since none has a default.
- **The tests** build the command line from the names in the failed run's log with placeholder values, require the reference output, require the sentinel values never to reach the log, and require each missing, misspelled, abbreviated or malformed argument to exit 2 with the right message and write nothing.

### Each run writes its own prefix (M5c-0)
The rerun fix above deletes an output path and then writes it, so a rerun that fails after the delete, or between the two outputs, loses the last good output and can leave a CSV without its matching hash. Nothing reads the output yet; the Redshift load (M5c) must not be the first reader to find out. **Superseded design:** the job no longer deletes anything.
- **Layout.** A run writes only `<--output>/<JOB_RUN_ID>/shape_params.csv/part-00000`, `…/shape_params.sha256/part-00000` and `…/_complete.json`, where `--output` stays `s3://<bucket>/m5/shape`. The run id is Glue's own `JOB_RUN_ID` (`jr_` and 64 lowercase hex digits, validated by a strict pattern because it becomes a path segment); Glue appends it to the script's arguments (the first failure's log listed it as ignored), so the job's default arguments and the plan do not change. The earlier layout (`m5/shape/shape_params.csv`, from runs 2 and 3) has no completion record and is ignored by the loader.
- **Completion record.** `_complete.json` is created last, in one call and without overwrite, after both outputs are closed: `schema`, `run_id`, `params_sha256`, `rows` (48), the two output sizes by key relative to the run prefix, the job's arguments and the completion time. No account, bucket, URL or ARN. S3 makes an object visible when its stream is closed, so the record exists whole or not at all. A failed record write does not close its stream (no partial record).
- **No deletes.** `_delete` is gone, an existing run prefix (with or without a record) is refused with nothing written, and a failed run leaves its partial output where it is, without a record. Two runs never touch the same keys.
- **Tests** (red first): two runs to one output leave both complete and the first byte-for-byte untouched; the same id twice, or over a prefix without a record, is refused and changes nothing; a malformed id (13 shapes, including path tricks) is refused before anything is written; a fault between the two outputs, and a fault while writing the record, leave no record, and the previous run intact; the record is created when both outputs already exist; `.delete(` does not appear in the job. Reading the record, the hash (twice) and the 48 rows is the loader's job and belongs to M5c-2.
- **The next plan** is the script object (ETag and `version_id`) and nothing else, which `glue_plan_check.py --change update` already enforces; new tests pin that a change of `--output` or a `--JOB_RUN_ID` default argument is refused. The role keeps `s3:DeleteObject` on `m5/*` for now: narrowing it is deferred until the first run-scoped run has shown which deletes the output committer needs.

### The Redshift stack as built in M5c-1 (amendment, 2026-10-11)
The owner's decisions of 2026-10-11 and what the code now says. Nothing here is applied; the stack has a plan check, policy rules and a CI plan, and its first apply is a separate approval.

- **8 RPU base and 8 RPU maximum, not 4 and 8.** "Compute capacity for Amazon Redshift Serverless" lists the ten Regions where a 4 RPU data warehouse can be created; Canada (Central) is not among them (an October 2025 announcement gave it an 8 RPU minimum, where it had been 32). Base capacity moves in steps of 8 from 8 to 512, so 8 is a valid maximum, and a maximum equal to the base means no autoscaling, which suits a load of about 1 KB. The default stays unacceptable (128 RPU, $52.80 an hour): the plan check and a Rego rule refuse a workgroup whose base or maximum is unset, outside 4 to 8, or "-1".
- **Cost while queries run: about $3.30 an hour** (8 RPU at $0.4125, per second, 60-second minimum each time compute resumes), nothing while idle. A 20-minute session is about $1.10, so each session needs its own go. `max_capacity` is the only ceiling on the rate.
- **The usage limit is a backstop, not a cap.** AWS: an RPU-hours limit "doesn't set a ceiling on capacity" and acts (log, alert, turn off user queries) once reached, at a time it does not document. It is `serverless-compute`, daily, **4 RPU-hours** (30 minutes of compute at 8 RPU), breach action `deactivate`. The earlier 3 RPU-hours and "$1.24 a day ceiling" are withdrawn: at 8 RPU 3 hours would be 22 minutes, and no daily cost is guaranteed.
- **Decisions D1 to D4.** D1: Redshift loads the Glue shape parameters from a completed run plus the batch store's published gold curves and revisions, found through `current.json` and the manifest, never by listing. D2: the loader is a script the operator runs; no Lambda, no new compute stack. D3: the run id is Glue's `JOB_RUN_ID`, a required argument of the job (M5c-0, done). D4: the Glue hardening came first (M5c-0, accepted).
- **The COPY role** (`ecp-redshift-copy`, workload boundary, trusted by `redshift.amazonaws.com` and `redshift-serverless.amazonaws.com`, as the Redshift Serverless IAM documentation requires): read-only. `s3:GetObject` on `m5/shape/jr_*/shape_params.csv/part-00000` in the Glue bucket and on exactly `store/runs/*/*/gold/current.parquet`, `.../revisions.parquet` and `.../curves.parquet` in the batch bucket (`runner.py` writes the third, the forward curves built from the shape parameters, besides the other two; D1's "gold curves" include it), plus `s3:ListBucket` with an `s3:prefix` condition on the same patterns in each bucket (COPY lists the bucket and treats its path as a key prefix; "COPY from Amazon S3" says so). The gold keys hold run ids that do not exist when the plan is made, so the grant is the pattern; exactness comes from the loader, which takes the key from the manifest, requires exactly one listing match with the recorded size, and checks the hash. No KMS or batch-stack change is needed: the batch bucket uses SSE-S3 and its only bucket policy denies requests without TLS, which COPY uses.
- **The Data API caller** (`ecp-redshift-data-api`, workload boundary): `redshift-data:ExecuteStatement`, `BatchExecuteStatement` and `redshift-serverless:GetCredentials` on `workgroup/*` of this account and Region **only where the workgroup is tagged `stack=redshift`** (the workgroup ARN holds an id unknown at plan time; the plan check pins the tag), plus `DescribeStatement`, `GetStatementResult` and `ListStatements`, which take no resource. No `CancelStatement`, no administration of the warehouse, no S3, no `iam:PassRole`. **Proposed trust:** this account's `AdministratorAccess` Identity Center sessions only (`Principal` the account root with `ArnLike aws:PrincipalArn` on `role/aws-reserved/sso.amazonaws.com/*/AWSReservedSSO_AdministratorAccess_*`, the pattern of the break-glass role without the management account and without a source-identity requirement). The operator runs the loader as that role.
- **The service-linked role is declared.** Redshift creates `AWSServiceRoleForRedshift` the first time it is used in an account, and no stack in this account has used it, so `aws_iam_service_linked_role.redshift` is a resource and both warehouse resources wait for it (the ECS pattern of ADR-0022). If the role exists, the create fails with EntityAlreadyExists and the fix is an import in its own reviewed change. It cannot carry a boundary.
- **Teardown without a final snapshot.** The provider's namespace has no final-snapshot argument; at v6.68.0 its delete calls `DeleteNamespace` with the name only, so a destroy takes no snapshot and cannot be asked to. The data is synthetic and reproducible from the repository. The earlier `skip_final_snapshot` wording was wrong. **Before any destroy, `aws_iam_service_linked_role.redshift` must leave the state** (`terraform state rm`, or a `removed` block with `destroy = false`), so the role stays: AWS refuses to delete it while Redshift resources exist, other uses in the account may depend on it, and a destroy plan that tries to delete it is a stop. The `--change destroy` check (planned) accepts exactly the stack's other 17 resources as deletes.
- **Eighteen resources, one stage:** the VPC (10.43.0.0/16, apart from the batch stack's 10.42.0.0/16), its default security group emptied, three private subnets in the first three Availability Zones the account reports (a precondition), a route table with no route and three associations, a security group with no rule, the two roles and their inline policies, the service-linked role, the namespace (`ecp-redshift`, database `ecp`, the COPY role associated), the workgroup and the usage limit. No gateway, NAT, endpoint, address or route; a Rego rule refuses them for this stack.
- **Checks.** `scripts/redshift_plan_check.py` (create mode) pins the capacities, the limit, the tag and the wiring: each value that ties one resource to another is exactly the reviewed value or, when unknown at plan time, an exact reference to this stack's own resource in the plan's configuration (as `glue_plan_check.py` does since #68); the reference sets Terraform lists for the subnet list and the associations are modelled on the Glue stack's real plans and are confirmed by the first real Redshift plan, before its hash is reported. `policy_gate.py --stack redshift` runs the existing rules plus new ones (capacity, IAM-only namespace, no way out, a trust never names everyone); CI plans the stack read-only as `terraform-plan (redshift)`, informational like batch and glue until applied; the plan role is ReadOnlyAccess and needs no change.
- **Still unverified:** `COPY` with no internet path (the first session's first statement); that the workload boundary lets the Redshift service use the COPY role (the offline R2 tests pass; the first session proves it); whether `ecp-readonly` may read the budget (the budget step reports a denial and stops).
- **Planned for M5c-2, not built here:** the loader treats an empty or unparsable `_complete.json` as not complete (a failed write on a local file system leaves an empty file), with a test.

**The admin name `admin`: a documented exception.** The namespace reports `adminUsername: "admin"` although the stack sets no admin attribute (`admin_username` is computed by the provider). It is accepted, because: (1) renaming it needs a password change alongside, which this design rules out (no password and no secret in state); (2) **no password or secret was set**: `adminPasswordSecretArn` is null and `admin_user_password`, `admin_user_password_wo` and `manage_admin_password` are null in the plan and the state; (3) **there is no network path to a password login**: the workgroup is not publicly accessible, the VPC has no internet gateway, NAT gateway or `0.0.0.0/0` route, and both security groups have 0 inbound and 0 outbound rules; (4) access is IAM only, through the Data API, which maps the caller's IAM identity to a database user with `redshift-serverless:GetCredentials`. The wording elsewhere in this ADR is corrected to "AWS's default admin name, no password set, no network path". The same read-back reports `kms_key_id = "AWS_OWNED_KMS_KEY"` (the AWS-owned key, which is what the service reports when no key is configured; none is).

**The SQL (`sql/redshift/`).**
- `ddl.sql`: `ecp_shape_params`, `ecp_observations`, `ecp_revisions`, `ecp_curve_points` and `ecp_load_log` in `public`, idempotent, with each table's columns in the order of the file it is loaded from (COPY maps by position). Shared with the local Postgres, which runs the same file in the tests.
- `queries.sql`: the five queries of this ADR as one shared file, run against the local Postgres on a synthetic three-version store and compared with Polars. **One adjustment:** "a rolling percentile" is a percent rank within the calendar month of each curve position (`PERCENT_RANK() OVER (PARTITION BY curve, position, month ORDER BY price)`): a rank function ignores a window frame and `PERCENTILE_CONT` is not a Postgres window function, so a true N-day rolling percentile is not shared SQL. It is still the one window function.
- `copy.sql` (Redshift-only, parsed with `sqlglot`): four `COPY` statements, each from **one full key** (the CSV with its header skipped; the three parquet files), with `IAM_ROLE` the namespace's `ecp-redshift-copy`. Never a prefix, a wildcard or a manifest.

**The loader (`scripts/redshift_load.py`).** Operator-run, no Lambda. Two identities: S3 is read as the operator; the statements go through the Data API as `ecp-redshift-data-api`, assumed for an hour (that role has no S3 access, and the COPY runs as the warehouse's role). Before the first statement it checks, failing closed: the shape run is the named one or the newest with a valid `_complete.json`, and an **empty, truncated or unparsable record means not complete** (a failed write on a local file system leaves an empty file), as does any record that is not exactly the reviewed shape; both outputs exist with the recorded sizes; the `.sha256` object equals the recorded hash; the CSV is exactly the 48 rows; the canonical text rebuilt from them hashes to the recorded hash (the hash twice); the gold files come from `published/current.json` and the manifest, whose hash is verified, with each key taken from the manifest and required to be `runs/<id>/<attempt>/gold/<name>.parquet`, each file's bytes, row count and columns checked; and, before each COPY (and once more right before the first), a listing with the full key as the prefix returns exactly one object with the verified size. After the load it reads back: the 48 shape rows must rebuild the hash and each gold table must hold the manifest's row count. Any failure after the load began empties the tables. Output and messages never show an account ID, a bucket name or a full run id. Tested with moto and an in-memory stand-in for the Data API; **no real Data API call has been made**. The first session runs it for the first time.

**Still unverified:** `COPY` of the parquet files (column type mapping, the timestamps with time zone, the decimals) and of the CSV, with no internet path; that the workload boundary lets Redshift use the COPY role; the queries on Redshift itself, compared with the local results.
